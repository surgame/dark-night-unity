# Unity验证内存事故与保护

> 本页保留原批次日期、源码／Player身份、协议和实际验证结果。2026-10-09整合后，现行职责由[合同／操作入口](../UNITY_CLI_WORKFLOW.md#内存门控)承接；未完成项查[当前执行状态](../DEVELOPMENT.md)。归档不核销待验或借用旧通过数。

2026-10-07，在地面玩法收敛的正式商店UI验证中，两次打开F10后Editor内存耗尽，分别产生14:43和14:48附近的崩溃记录。用户观察到其他应用被系统结束，截图显示Unity主进程约16,738.8 MB、系统内存92%。第二次提交发生在尚未充分分析第一次失去测试回执时；不能将该重试视为正常的验收续接。两个批次都没有完整通过结果。

## 已确认原因

事故日志副本约421,034,871字节、2,795,919行，含82,089条TMP缺字警告。`Inconsolata SDF`缺少中文，警告对象是控制台 `[LogText]`。Bootstrap实例开启插件 `ShowApplicationLogs`，所有Unity警告通过 `Application.logMessageReceived → ConsoleSystem.SubmitLog → SmartConsole.LogCommand → UIGenerator.GenerateLogMessage` 再生成一条文本对象。新文本继续缺字、警告和生成，且插件没有日志数量上限，形成反馈循环。

首个 `OutOfMemoryException` 位于 `TextMeshProUGUI.OnEnable` 的委托注册与日志Prefab克隆链，后续同时发生布局和原生内存分配失败。该堆栈、警告数量和插件源码共同支持上述根因；目前没有证据把这两次事故归因于地图生成、多个完整Editor并发或YYGC状态复制。截图中的Unity进程组包含Editor辅助进程，不能据组内进程数认定开了3个项目。

证据副本及有限摘要在 `artifacts/ground-baseline-20261007/memory/`。副本启动参数已脱敏；原始系统日志未修改。用户所见其他应用结束未取得逐应用系统事件证据，因此不推断具体进程、时刻或杀进程主体。

## 游戏侧修复

`SmartConsoleLogBridge`在正式装配时关闭插件的无界应用日志订阅，转入游戏侧有界适配：待处理最多200条，每帧最多12条，单条最多2048字符，面板达到400条后轮换清空。插件公开的日志查询同时用于检查直接写入的显示数量。完整原始日志仍保留在Unity日志文件；F10只承担有界展示。

只阻断控制台LogText／AutocompleteText自己的TMP缺字警告反馈，其他对象的正常警告、异常和错误维持原等级。Latin字体使用运行副本，追加Microsoft YaHei中文回退，动态字体单张1024²图集，不开放多图集；副本设置DontSave，不改变作者字体、SC.Prefs、Prefab或YYGC。退出时解除订阅、释放队列与运行时字体；TMP副本释放前先断开共享作者图集和材质引用，避免触发资产销毁。

## 本机验证保护

`tools/ground-baseline/watch_memory.py`是单次验证的独立进程，先通过Unity CLI核对目标PID和项目，每秒记录Editor私有内存、工作集、可用物理内存和提交余量。32 GiB主机使用以下停止阈值：

| 指标 | 阈值 |
| --- | --- |
| Editor私有内存 | 达到8 GiB |
| 可用物理内存 | 低于6 GiB |
| 系统提交余量 | 低于8 GiB（2026-10-09 用户调整） |

2026-10-09 用户要求把系统提交余量门控提高至8 GiB；Editor私有内存8 GiB上限与可用RAM6 GiB下限保持。监控与照明静态编译入口共用 `watch_memory.py` 的 `LIMITS` 和 `memory_breach`；静态编译启动仍额外保留该阶段预计分配量。下方2026-10-07验证及此前照明证据采用当时4 GiB提交余量停止线，历史样本和通过结论不按新阈值改写。

任一越界会写 `breach.json` 并请求停止本项目Play，随后禁止新验证；不会结束其他应用。该保护请求仍依赖Editor响应，不能保证挽救已失去响应的进程，所以重点是消除反馈源、限定短时探针，并在每批前检查余量。构建期间停止Play不能可靠取消同步BuildPipeline任务；启动高内存构建前必须保留额外余量，不能以监控存在为由冒险启动。

先通过有界队列和过滤测试，再在监控下用一条中文日志、三次F10开关验证，不重建大规模真实日志风暴。通过后只恢复一批商店UI验证；构建、Player进程及更大联机矩阵按实际余量另行门控。保留原失败、修复后的结果及内存样本，不将“未再次崩溃”扩大成所有场景内存安全保证。

当前队列／过滤6项、真实中文F10探针1项和正式商店UI1项已通过；合并地面玩法与输入／跳跃共31个不同Editor检查通过。监控1018次、约17分钟，Editor私有内存峰值4.515 GiB，可用RAM最低10.330 GiB，提交余量最低5.190 GiB，未触发保护；最终已退出Play并结束这一单次监控。机器摘要见[本批证据](../evidence/ground-gameplay-baseline-20261007.json)。尚未执行Mono构建及独立进程联机，本轮无IL2CPP或双机器结论。
