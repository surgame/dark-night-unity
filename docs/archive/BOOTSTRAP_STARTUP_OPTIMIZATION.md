## 问题与收益依据

启动链已使用UniTask，但24个对象Prefab和6个UGUI面板按循环逐项等待资源加载。主菜单在它们以及飞船UI准备完成后激活。真实提供器的三次隔离对照平均为对象2.604秒→0.113秒、UI资源0.666秒→0.109秒；仅资源请求预计节省3.05秒。该对照原生资产缓存已热，不含场景、装配及首次菜单渲染，不能作为完整启动成绩。

## 执行切片

1. 增加默认关闭的有限启动采集：统一单调时钟，记录Bootstrap Awake、Editor进入Play、内容、场景、对象资源、UI、菜单激活、首次Canvas渲染准备和会话Ready。先在原串行实现采集三次基线。
2. 用UniTask同时启动独立资源请求。一个请求失败或取消时取消其余请求，等待每个请求收尾，再统一释放成功租约；全部成功后才把租约移交调用者。
3. 对象资源准备复用现有YYGC `PrepareAsync`。UI仅并发预加载原六个Prefab，实例仍走UGUIManager原顺序创建、绑定和激活。UI预加载租约覆盖实例创建过程，之后归还；不把UI传入禁止UI的对象Prepared接口。
4. 编译并运行失败、取消、晚完成及所有权移交测试；复用既有原生UI和对象资源回归。用相同采集器、Editor配置和场景采集三次修复后结果，并验证菜单及正式Host启动。
5. 检查差异、资源引用、架构与单文件上限；将实际结果、失败和验收边界写入本文及开发状态。只在游戏侧修改，不新增R3启动链或线程池中的Unity创建。

## 判定与保护

- 首次菜单Canvas渲染准备是CPU侧渲染边界，不代表GPU呈现时间；同时报告从Bootstrap Awake和Editor进入Play计时，域重载不计入二者。
- 比较实际对象/UI阶段与完整菜单阶段，不把会话Ready之后的预热或隔离估计算作菜单成绩。若阶段间线程等待变化，保留并说明。
- 要求六个面板数量、顺序与可见性合同相同，失败与退出Play无未归还的新租约，正式Host能Ready。预估目标为菜单2～3.5秒，实际结果另记，不作为预先保证。
- 不运行IL2CPP，不把本轮Editor结果当作Player、前台性能或双机器验收。原有缓存和正式证据保留；临时产物按AGENTS统一归档规则处理。

## 实施与验收结果

对象资源通过 `Runtime/Framework/StartupResourceBatch` 并发准备，全部收尾后统一移交。`ObjectSessionResources`仍按输入顺序建立定义索引。`Runtime/Framework/SessionUiResources`只并发加载六个面板模板，Entry原UGUIManager创建、绑定和激活顺序保持。没有新增程序集或包引用；第一次编译发现Entry未引用Addressables后将UI租约helper移至现有Runtime层，后续编译无错误／警告。

相同Editor、Bootstrap、域重载设置与0.1秒模拟延迟下，各采集三次：

| 指标 | 原串行平均 | 修复后平均 | 差值 |
| --- | ---: | ---: | ---: |
| Editor进入Play → 首次菜单Canvas渲染准备 | 6.114秒 | 3.318秒 | 减少2.797秒，约45.7% |
| Bootstrap Awake → 同一菜单边界 | 7.212秒 | 4.430秒 | 减少2.782秒 |
| 对象资源准备 | 2.377秒 | 0.086秒 | 减少2.291秒 |
| UI初始化（含顺序装配及飞船UI） | 0.790秒 | 0.260秒 | 减少0.530秒 |

原实现菜单三次为6.151／6.121／6.071秒；修复后三次为3.389／3.111／3.453秒。计时是CPU侧渲染准备而非屏幕像素呈现；原生资产缓存已热，不宣称全冷磁盘或Player提速。其余启动阶段仍保留在原始时序中，没有扣除异常等待或移动计时起点来放大收益。

- 定向Editor回归50/50：新增8项批次并发／所有权／失败／取消／晚完成／清理异常检查、2项真实UI模板检查，以及现有原生UI、对象工厂／装配／退休、事务和会话生命周期。
- 架构守卫741个手写文件、16项自测、0命中；手写文件均不超过300行。Unity6000.4.9f1编译无错误／警告。
- 三次菜单均为相同六个面板，顺序0～5，可见性只有MainMenu开启。实际正式按钮打开帮助、返回菜单并新建Host通过；Host Ready、世界副本和专属主角已建立，UI实例仍为6，检查范围内运行错误匹配0。
- 退出Play后会话网络实例0、UI实例0，Bootstrap未修改，采集自动关闭；加载设置仍0.1秒，资产字节SHA-256保持。
