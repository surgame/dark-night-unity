# 内嵌矿层地图迁移执行方案

2026-10-05执行状态见[实现与测试](../MINERAL_MAP_MIGRATION_IMPLEMENTATION.md)：两层局部流、原生矿格唯一状态与v19恢复已实施，Editor105/105、当前Mono正常两人30/30／四人38/38／弱网两人30/30；下方调查基线与计划保留，专项性能等未验边界以实现页为准。

日期：2026-10-05。调查基线：`ft-20261004-embedded-minerals` 的 `3076027`，矿床实现检查点为 `e0419d2`。本文件是拟执行方案；本轮只调查源码和编写文档，没有实施迁移、修改依赖、运行 Unity 或新增验收结果。

可以迁移，而且已有规则、美术、分页、格业务组件及地图网络协议能复用。难度属于中等规模架构迁移，主要工作是更换状态所有者、接通独立矿层传输、迁移采集与保存合同。不能将它当作增加一个配置开关。当前 245 项 Editor 和正常两人／四人结果只支持原对象方案，不支持本方案通过。

目标是一个独立的权威矿层地图。YYGC 会话负责生命周期、权限、业务命令和事务；矿层 ARDMap 及其 GridBusinessStateStore 唯一拥有矿格状态。客户端按区域接收副本，AnyRuleD 按页面绘制。不按矿床或区块创建大量 YYGC ObjectInstance。

默认收益、采集耐久40、每轮产量1、工具伤害和挥镐时序保持当前原生配置。矿层材料不参与角色或飞船身体碰撞；前景仍负责遮挡和通行。铜、银、钻石继续只用于表现样板。

当前矿床总容量按格守恒的生成结果可先转换成矿层蓝图。扩大表示容量不改变正式生成密度或经济总量。高密度夹具单独生成，用于容量验证，不冒充新的正式地图分布。

矿格耗尽时清除矿层格。原生空格不能保留业务组件，所以耗尽事实由显式最终空格和内容身份变化表达，保存后不能被初始蓝图重新补回。普通扣耐久和未耗尽的取矿不更换内容身份。

## 地图加载与网络方案

房主先常驻当前有限地图的权威纯数据，客户端局部订阅与加载。当前320×192共61440格，首轮容量合同可按这个有限坐标范围制定。不能把原生组件的最大记录数当成实测性能结论；暂不增加房主磁盘分页或无限世界能力。

前景和矿层共用一个区域策略，但保留各自的内容目录、流会话、流代次、提交游标与区块版本。游戏层明确它们属于同一个星球与世界代次。两层消息必须可区分，旧流消息不能安装到新世界或另一层；流提交号与权威地图提交号不直接比较。

拟优先验证的游戏侧接法：矿层使用独立的游戏广播消息类型承载原生 AMP1 字节，复用 MapInterestService、MapProtocol 和 ChunkReplicaStateMachine。只补连接生命周期、消息分流和有限发送预算，不复制规则求解、协议编解码或副本安装算法。现有适配无法直接承载两层的源码证据见上表。前景动态订阅可先用现有公开 MapWireMessage／MapProtocol 控制帧发送，必须探针验证代次切换及首次订阅行为。

这一路线尚未验证，因此 P0 不通过时不继续业务迁移。若游戏侧窄适配造成明显重复，或现有接口无法满足动态订阅与多层消息隔离，应形成 FishNetMapTransport 的具体扩展方案。框架文件及 .deps 内源码、补丁、升级均受 AGENTS.md 的事先同意约束，本方案不授权修改它们。

区域策略必须具备以下行为：

- 初次区域来自可核验的出生点、船体或落地点，避免等待玩家 Ready 后才确定区域、又等待区域后才能 Ready 的循环。
- 客户端请求经服务端限范围、限频率和限区块数；不由客户端请求扩大权限。
- 相机范围、交互范围、移动预取范围明确，保留四角规则所需的邻格缓冲。
- 区域按区块移动，使用保留边界与预取，避免每像素移动都重订阅。当前原生 Subscribe 会重置流代次和基线，要测快速移动的重复流量。
- 初次 Ready 等待两层必需区块与当前相机实际绘制。普通换区不反复创建玩家或切换世界 Ready；未取得数据的目标暂不可交互，前景 Unknown 不能被当作可通行空地。
- 断线、撤权、换图和世界加载明确退休旧副本与页面。再次进入区域必须取得当前状态，不从过期客户端缓存恢复矿物。

矿格退出完整 YYGC 世界投影后，会话仅保留矿层身份、内容摘要及必要准备信息。初次基线和动态状态走区块流，不能把全图矿格再塞回会话元数据。AMP1 schema2是否可保持由 P0 真实编码往返确定。

用户若要求 worktree，采用薄 worktree 开发与 Local 单一 Unity 验收通道。新工作分支按创建当天的 `ref-YYYYMMDD-mineral-map` 规则命名并检查重名。当前实现分支、main、历史证据与已有用户工作不自动集成或推送。

## 采集事务与目标合同

目标由星球／地图身份、世界与地图代次、明确层、格坐标、前景内容身份和矿层内容身份组成。矿区 ID 如保留，只作静态引用或设备任务归属，不能充当实体存在性或授权证明。客户端不提供权威伤害、储量或奖励。

本地选择与服务端命中使用同一有限射线几何。查询前景最近真实坡形，并沿有限射线检查矿层格，退出扫描全部矿床数组和按实体 ID 反查身份的路径。两层相关格必须已知；前景遮挡保持现有语义。

提交器统一拥有候选校验、地图安装、回滚接线和延迟通知，规则计算只返回最终格、最终业务值及待发奖励。候选读取依据最终格是否为空，退出“耐久为零等于格为空”的固定判断。墙壁规则在耐久归零时清格并给出已有掉落；矿物规则在耐久归零时减实际储量，尚有储量则保留格并重置耐久，最后一份才清格。不复制两套提交器，也不为每种材料创建脚本物体；首批采用明确的两个规则分支，不预建任意效果插件框架。

例：矿格剩余3、耐久10，收到伤害10后，规则产生“剩余2、耐久恢复40、格保留、奖励1”的候选；墙壁在相同耐久与伤害下产生“清格、按墙壁配置给出奖励”的候选。奖励候选先检查货袋容量，再与地图和角色状态一同提交。示例沿用当前配置，不授权改变正式数值。

单次采集先检查当前地图、工具能力、范围、版本及最终货袋容量，再准备角色与一层地图候选。耐久归零后扣实际储量；剩余量大于零则重置耐久，否则清矿格。地图安装成功、对象状态安装成功后才发变化通知和反馈。YYGC CommitAll 的外部安装回调仍只组合一张地图。

当前爆破仅作用前景，本方案不新增背景矿物爆破产出，故不要求单个普通采集事务同时修改两张地图。未来确有双层编辑需求时，需要单独证明多地图准备和无失败安装能力，不能直接串联两个 Commit。

矿工设备的旧 TaskTarget 依赖矿床 EntityId，也必须迁移为明确的矿格或静态矿区任务引用。保持现有工作位、工具伤害、容量和交货语义，不扩大为完整新寻路路线；相关存档与投影字段一并更新。

## 保存与世界切换

拟下一候选采用游戏协议25／存档v19，AMP1 schema2以 P0 结果为准；实际版本由开工时基线核对后确定。不自动适配v18，不删除用户旧档。

矿层保存使用稳定材质 GUID 或带 GUID 的调色板、冻结初始容量、最终矿种格、业务偏差及必要内容身份。使用有界区块数组或紧凑记录表达数据，先测量最坏体积再冻结文件上限。当前4 MB整档限制必须纳入检验，不能只放宽矿格数量而漏掉JSON、内存或解压上限。

恢复先解析和校验两层及对象候选，再准备两张地图与对象资源，最后切换一次世界代次。现有 ObjectSessionPersistence 的单地图替换顺序需要审查，不能只追加第二次 Replace。候选阶段可抛错；安装阶段避免重新分配、加载或验证会抛错的资源，通知在所有所有者接管后发布。用故障注入验证失败保留原世界。

最终空格明确覆盖初始矿格。新代次拒绝旧命令，重进区块使用新的基线；不能把网络的临时流代次或本地 TileId 直接当作持久材质身份。
