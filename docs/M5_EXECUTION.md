# 从当前实现连续推进到 M5

更新：2026-09-11。执行基线为 `3195495`：M0 已完成，M1 规则／文件存储已验证，M2 只有权威业务服务，尚未构成可玩联机。本文是后续执行主入口；DEVELOPMENT 保留阶段定义和历史证据，MULTIPLAYER／MIGRATION_PLAN 保留产品合同，不在每批重写全部方案。

## 本次评估与简化

已有 1260 项独立回归、37 项 Editor 测试和正式 GuidFirst／GuidV2 接入探针可直接复用。剩余关键路径是“同切点展示数据 → 正式网络装配 → 必要可操作视图 → 完整关卡 → 恢复与交付”。继续按每个基础类单独交付会延后发现集成问题；重复 M0 框架研究、每条断言重建 Player、把 M4 的身份／epoch 推迟到 M3 后都增加返工。

执行调整：

- M2 首批一起落实展示副本、发布次序和真实时间累积；随后的网络 DTO、服务端身份、Ready 和 Entry 装配作为同一批接通。握手／epoch／连接代次从首个连接生效。
- 将 M1 剩余存档产品接入并入 M4；保留已验收的文件和规则实现，不再独立建立一套保存服务。
- M3 按共用绑定和动画合同集中处理 6 类角色、5 类建筑、4 类工位。先校准 Worker／Archer／HUD，再扩展其余资源；已有人工 Prefab 不被初始化器覆盖。
- 只维护一套正式进程驱动和报告格式，M2 建立，M4 增加场景，M5 从同一套驱动复跑。Sample 只作为可读实现参考，不被正式代码引用。
- 每个依赖就绪的代码批次统一导入／编译；需要新组件的资产随后批量创建／绑定／保存。通过后只因输入改变或失败重跑受影响验证。多进程复用同一 Player，不为每个操作重新构建。
- 不新建通用任务调度器，不预建分块、增量、平台大厅或房主迁移。可靠完整投影先实测字节与吞吐，超过明确阈值才调整传输。

“直达 M5”表示以下批次连续执行到交付门槛，不表示可以跳过 M2–M4，或用当前单元测试签署 M5。现有 16–26 人日基础估算暂不按工具调用减少同比下调；完成 M2 实测后再重估。

## 验证与运行组织

每批开工记录基线提交、用户工作区差异、受保护资源哈希、实际依赖和对应退出条件。先集中写入代码与共享回归；然后一次 Unity 编译及 `.meta` 生成；需要生成注册或新组件的资源操作按依赖继续。失败停止相应链路并保留报告，修正后只重跑受影响部分。

仓库根目录的常规检查：

```powershell
dotnet run --project tools/CoreRegression -- .
dotnet run --project tools/ArchitectureGuard -- .
unity command recompile --project-path Game --detach
unity command run_tests --mode editor --filter DarkNights.Tests --filter_type assembly --project-path Game --detach
```

CoreRegression 会引用并实际编译 C#9／netstandard2.1 Core。每个 detached 任务必须等同一个任务 ID 完成，不能将上述 Unity 行并发执行；自动导入已完成时复用编译结果。A1 不改发布入口，验证到独立回归和 Editor；A2/A3 起必须增加正式 Mono Player 的实际网络验收。

现有 `Dark Nights/Build/Windows Mono` 入口仅在完成对应装配后执行。`tools/test-game-startup.ps1` 只验证启动探针，不能替代待实现的正式玩法进程驱动。新驱动应接受既有构建目录及网络用例输入，输出逐项结果和日志路径；不重新打包、不改玩家存档。旧 Sample 弱网工具可复用外部进程组织方式，但正式断言必须读取真实游戏结果。

完整矩阵仍以 [DEVELOPMENT 的验收矩阵](DEVELOPMENT.md#验收矩阵)为准。每次报告区分代码已实现、独立／Editor 已验证、Player 已验证和待实测，不用历史双后端探针替代新增类型的 Player 验收。
