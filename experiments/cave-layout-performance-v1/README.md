# 预设房间与随机洞网 · 四方案性能页

2026-11-01，CL-01／08独立浏览器实验。用户要求解释连续轮廓与大块直拼的区别，对连续轮廓、直拼、过渡及WFC制作性能页，并考虑较多已确定地形点／洞室／房间时的资源成本。`index.html`为独立单文件页面；聊天预览同源。旧六方式样板及全部交互状态保留。

## 与上一页的实现区别

上一页的大块同样现场计算参数曲线，没有证明缓存收益。本页实际构造二维图、缓存同一形状的网格并引用实例，同时提供合成区块和模板实例两种渲染路径。

| 方案 | 本页真实执行 |
| --- | --- |
| 连续轮廓 | 根据共同房间／连接图创建全图标量场，对自由部分平滑两轮，按64×64世界单位提取独立区块；固定房间的采样被冻结，实际边界不得变化 |
| 大块直拼 | 对共同图直接确定匹配端口，选择整块形状；每图同形状只网格化一次，多次引用，之后可统一烘焙区块 |
| 大块＋过渡 | 自由节点采用24×24核心，预设房间保留32×32；用4或8单位连接段适配两端宽度，模板网格实际复用 |
| 大块WFC | 对共同二维邻接图的候选执行加权熵、版本堆、四向约束传播，锁定预设房间后选择合法组合；与直拼共享同一个整块候选库 |

连续轮廓负责逐图产生几何形状；大块负责重复使用完整形状，区别在数据表达与复用。两者可产出接近的外观。WFC属于候选选择方式，也可以用于核心＋过渡的库；本页WFC使用整块库，不能据此推导WFC天然需要更多素材。

本例连续轮廓是二维标量场实现，前页为一维三次曲线。本文性能只代表当前源码，不是所有连续轮廓实现的复杂度下限；全图采样、轮廓提取、数组复制及缓存均有进一步优化余地。

## 共同输入

- 128／512／2048个活动位置，分别落在16×12、32×24、64×48宏观格中；每格32单位，几何采样间隔2单位。
- 同一种子先产生连通树，再补部分邻接边形成分支和回路。四方案共用节点坐标、邻接、锁定房间身份和位置。
- 预设房间约占三成；32个房型由16种开口拓扑×两种作者形状组成。为隔离连接问题，锁定房间位于棋盘偶格，不直接相邻。不是任意相邻预设房间可解的证明。
- 标准端口只有一种宽度；混合端口有半宽3／4.5两类。固定房间的开口、形状和位置在四方案中保持，连续场平滑也不能改其网格。
- 自由区域的轮廓、端口及模块选择不同，四方案不是逐像素同形；资源量和可见几何量一起报告，不把全部计时差归因于算法名称。
- 每轮种子增加101，四方案共享该轮输入并轮换执行顺序。作者图生成在四方案计时之外，不向某个方案分摊。

2048位置、混合端口、种子271的代表图有602个锁定房间、2458条连接、411个图回路。这里只核对图与形状／端口合同，不签署角色通行、跳跃或返程。

## “节省tile”的三个口径

1. **形状配置库**：连续轮廓不额外建立terrain边缘图块库；直拼／WFC标准端口最多48项，混合端口最多243项。核心＋过渡分别为60／72项。它们是本例配置数，不是必须手画的图片数。
2. **地图中的几何引用**：连续轮廓引用每图独有区块，大块引用模块和过渡。引用更少不等于缓冲更小，也不表示作者节点数减少。
3. **最终顶点和有效载荷**：同一材质下，整图独立几何与复用源网格＋实例平移分别计数。此白模没有导入任何贴图，不能测出正式贴图、图集内存或最终美术制作量。

混合端口243项来自四向二态端口的全组合及三种内部形状；核心＋过渡把节点内部和连接宽度分开表达。共享旋转／镜像、过程参数或模块因子后，作者源可进一步合并。预设房型是所有方案共同成本，不能因使用连续轮廓就删除其资源。

## 实测方法

源码：`plan.js`创建输入及确定性拼装；`solver.js`是真实二维WFC；`field.js`保护预设并创建连续场；`mesh.js`提取网格、缓存源形状及烘焙区块；`gpu.js`上传／绘制；`benchmark.js`负责独立样本。只读复用原`dualgrid-cave-exploration-v1/dual-grid.js`的拓扑，原源码与原输出不改。

每个端口条件×每档规模先预热四条路径，然后正式16轮。共2×3×4×16=384个独立地图管线。每轮重新建立几何缓存，测的是冷CPU准备和同图实例复用，没有把跨种子热缓存收益混进结果。

| 阶段 | 计时边界 |
| --- | --- |
| 生成 | 连续场／直接规则／模块及连接选择／WFC求解，使用各自实际输入结构 |
| 几何 | 当前地图所需源模板首次生成，或连续场区块提取 |
| 分块 | 将模板引用合并为区块；连续方案已经是区块，只返回现有结果 |
| 冷CPU合计／分块就绪CPU | 从开始生成到分块结束的实际外层时间，不能由各阶段P50相加；纯实例流程可跳过分块，本页未把此值作为纯实例流程总CPU |
| 上传分块／复用 | 各自的实际GL分组、缓冲创建／上传与GPU同步；两条路径分开报告 |
| 单次绘制完成 | 960×600输出、256×160世界单位固定相机，剔除、提交、绘制及`finish`；每轮6个独立样本／路径 |
| 成组绘制 | 每组64次真实绘制，每次都`finish`，在组外记录起止；每轮4组／路径，交错后端顺序 |

表中绘制列是**64次整组完成时间**，P50／P95来自64个组，不冒充单次帧延迟或FPS。原始单次样本保留：当前约0.10ms计时粒度会产生0或小于粒度的数，页面按粒度标记。组内64次不是64个独立P95样本。

连续轮廓已经使用独立区块，其“实例”路径与分块实际相同；最终测量只执行一次，页面标为“同分块”。没有复制计时伪造成另一组测量。

WebGL2共用shader、材质、输出和相机，绘制包含空气面与边界线。实例按模板及空间块分组，实际重复使用源VBO；它减少缓冲，但可能增加draw calls。统一分块与实例路径的实际像素、上传字节分别核对。有效载荷是二维Float32顶点和实例平移，不含驱动、JS对象、双路径同时驻留、连续场临时数组、真实物理或贴图。

## 当前结果

最终原始数据：`records/1793538496522-measurement/raw.json`。硬件为Intel Core i5-14600KF／RTX5060Ti，Chromium149／ANGLE D3D11；输出960×600，实际GPU字符串及浏览器身份在报告中。内存预检可用物理内存约11.58GiB。不是Unity前台性能。

下表为2048位置、混合端口，冷CPU为16图P50／P95，资源对应代表种子271：

| 方案 | 冷CPU ms | 源形状用／库 | 分块MiB | 模板复用MiB |
| --- | ---: | ---: | ---: | ---: |
| 连续轮廓 | 94.10／99.45 | 0／0 | 6.43 | 同分块 |
| 大块直拼 | 28.85／29.80 | 216／243 | 6.59 | 0.84 |
| 大块＋过渡 | 20.05／22.20 | 68／72 | 5.86 | 0.23 |
| 大块WFC | 47.25／51.60 | 218／243 | 6.69 | 0.84 |

本例固定相机下，统一分块比分组模板实例的提交更快；模板实例则显著减少驻留源缓冲。布局冻结后无需每帧重跑连续场或WFC。加载成本、帧内绘制和资源制作量分别决策。

完整预设房间和复杂接口优先考虑核心＋短过渡；重视自由洞形且愿意逐图烘焙时可用连续轮廓；接口标准化时直拼也很节省。WFC只在确实存在多候选兼容选择时加入，库如何拆分可独立决定。
