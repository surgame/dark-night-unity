# 三种地形铺设与局部破坏性能样板

2026-11-01，归CL-01／08。用户授权“不同方案都试做一下，并相对评估性能”。本实验实现烘焙分块、分段边缘变形网格、16型DualGrid图集，提供同视图切换、共同破坏序列和实际计时。没有替换正式游戏渲染器、地图、碰撞、玩法、网络或存档。

## 共同输入与制作合同

- 地图为独立320×192格测试场，321×193二值格点；共60个32×32格区块。同一四角占据派生16个拓扑，5／10采用分离实角的固定策略。它不是正式生成器的地图，也未复制当前12坡形或圆化修饰器。
- 三种方式消费完全相同的占据和固定960×640、48×32格镜头。角色为原PNG三格高比例参照，未模拟移动、采集或碰撞。
- 沿用`美术素材/地图/20261030-flat-cave-kit/sources/`原岩面、路面、悬顶。原生输入尺寸分别1254×1254、1536×1024、1536×1024。原主角来自旧WFC包的282×309比例参考PNG。
- 运行测试采用确定性裁切／缩放的64×64岩面、64×4地表／悬顶条；统一16纹素／格。16拓扑乘4×4世界材质相位，派生288×288图集，其中256条是自动配置／裁切结果，不是256张人工tile。每格16×16，四周1像素延伸防串色，最近邻、无mipmap。
- 这些低分辨率派生图用于渲染实验，不是新画风定稿或正式tile。源字节不覆盖，裁切矩形、重建过程和SHA-256见`build.py`及`records/*-build.json`。
- 原包按整段弧长铺图；本样板把边缘缩为格内有界切线／法线条带，使用稳定局部锚点，内部岩面使用世界UV。它验证可局部更新的实现，不证明原包任意急弯、所有坡形或长曲线已经解决。

## 三种实现

| 方式 | 缓存与绘制 | 变化时实际执行 |
| --- | --- | --- |
| 烘焙分块 | 每区块一张512²RGBA纹理和一个四边形 | 浏览器用Canvas重新绘制受影响整页并上传；Unity用图集网格在GPU重绘受影响RenderTexture，不做CPU整页纹理上传 |
| 边缘变形网格 | 完整实格按每行合并岩面；边界独立条带，地面／悬顶独立材质 | 重建受影响区块的岩面及边缘网格，更新顶点／索引缓冲 |
| DualGrid图集 | 每个非空格一个图集四边形，按区块批量绘制 | 重建受影响区块的图集网格，更新顶点／索引缓冲 |

因此，本实验不是三条完全相同的代码路径，也不是三条各自的理论最优实现。完整岩体合并给边缘方案带来显著几何节省；DualGrid同样可以继续做完整区域合并、固定槽位局部缓冲更新或属性纹理方案，不能把本次顶点数写成算法的固有成本。Unity和浏览器的烘焙更新后端也不同，不能把两张表混用。

初始地图后分别从原图执行24次单点请求、12次半径2.2格爆破请求；其中16次单点、12次爆破实际修改地形，空操作不计更新样本。每次被修改格点只使其相邻四个图块失效；本实现为保持批处理，以32格区块为实际重建单元，不宣称只更新四个图块。切换显示方式保持相同破坏历史。

## 当前Unity实测

锁定Unity **6000.4.9f1**，**RTX 5060 Ti／Direct3D12**，单一后台Editor，无Play、无场景装配或切换。显式编译无错误，输入哈希和程序集常量`terrain-render-bench-20261101-v4`核对后执行。

每种方式3轮，轮换先后顺序；静态每轮预热5次、采样15次，共45次。初始3次、有效单点48次、有效爆破36次。保留全部样本，不剔除较慢结果。

| 方式 | 首次准备中位ms | 静态完成中位ms | 单点中位／P95 ms | 爆破中位／P95 ms | 策略纹理MiB | 网格含索引MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 烘焙分块 | 28.31 | 0.110 | 0.350／0.513 | 0.371／0.555 | 60.000 | 0.008 |
| 边缘网格 | 3.25 | 0.134 | 0.337／0.520 | 0.362／0.572 | 0.018 | 0.611 |
| DualGrid图集 | 7.00 | 0.103 | 0.330／0.534 | 0.320／0.474 | 0.316 | 7.367 |

记录位于`artifacts/terrain-render-bench-20261101/unity-r4/report.json`及`assessment.json`；展示副本是`measured-unity.json`。当前破坏终态的可见提交为4／11／4次、24／3690／17574顶点；内存列是整图60区块的有效载荷，不是这一个镜头的全部显存。

**计时含义必须保留：**

1. Unity读取浏览器导出的冻结几何。首次准备包含网格装配／上传和首次完成绘制；更新包含网格装配、上传、必要GPU烘焙、绘制和1像素同步读回。没有测C#侧轮廓提取、DualGrid查表或权威地形事务。
2. 静态完成时间包括CPU提交、驱动／GPU等待与读回，不能叫纯GPU耗时或换算成游戏FPS。差值接近计时底噪，不支持显著稳定帧优势的结论。
3. 只测地形。碰撞、照明／遮挡、草菇／流水动画、粒子、联网和存档均未纳入。没有执行正式Player前台或双机验收。
4. 纹理列是不压缩、无mipmap、整图常驻的策略缓存；网格列按顶点位置／UV和32位索引有效载荷计算。JSON、CPU数组、Unity对象、驱动开销、共享源／暂存纹理和其他场景资源未计入。正式流式加载和压缩会改变结果。
5. 本样板中的边缘方案性能可用，资源较省；高频任意破坏是否采用它，仍取决于正式坡形的局部轮廓提取、接缝与碰撞／光照连带更新。静态区预烘焙与可破坏区网格可以分区使用，不必整图单选。

浏览器计时另存`measured-browser.json`，来源为本机Chromium离屏WebGL；表中可切来源或在用户设备重测。浏览器更新还包含JS破坏计算和几何重建。不能用于证明Unity更新耗时，更不能把Canvas整页上传的额外成本转嫁给Unity的GPU烘焙实现。

## 核对、已修正问题及保留证据

- 三种方式使用同一破坏结果摘要；边缘网格及图集的58个未受影响区块几何／UV逐值保持不变，跨区块失效范围核对通过。
- 浏览器真实敲击／爆破后，局部变化以外的画面逐像素不变；三方式、736／360／320双主题、状态恢复和来源切换核对，未发生脚本错误。
- Unity初始和破坏后六张截图非空，三种方式在2像素光栅边界容差外无占据差异；远处上方／左右像素逐像素不变。不是允许正式素材存在2像素裂缝：这里只分离不同光栅化方法的边缘AA，不核销正式共边美术验收。
- 首轮宿主保存回送导致统计清空、预览包装未替换、角色比例参照悬空／切口靠下、后台Editor未重新编译，以及合并岩面后的浮点纹素闪动均已发现并修正。纹素闪动通过世界UV量化至稳定纹素中心处理；Unity烘焙采用直通复制混合，避免透明边重复乘alpha。
- `unity-r1`、`unity-r2`、`unity-r3`和原`input.json`保留。r1是960×560初轮；r2旧程序集的报告仍标560，不能引用为当前结果；r3发现局部变化以外的像素采样不稳定；当前有效结果只取r4。浏览器失败及中间截图继续保留在`records/`。
- 初始180秒内存监控及各批前检查通过，当前最低启动前剩余物理内存约10.25GiB；不采集系统提交余量。仅本任务启动的后台Editor已优雅关闭，没有退出用户原有Play或其他应用。

## 重建与验证

```powershell
python experiments/terrain-render-bench-v1/build.py <本聊天绝对路径>/terrain-performance.html
python <visualize技能>/scripts/render.py <片段路径> <预览路径> --force
node experiments/terrain-render-bench-v1/verify.cjs
```

`verify.cjs`完整运行会核对模型／交互，输出浏览器性能和冻结Unity输入；同名冻结输入已存在时要求字节一致，禁止静默更新。最终打包后用`node .../verify.cjs --final`核对当前包装／交互，不重复全部性能测量。

Unity测量源码仅在`Game/Assets/DarkNights/Scripts/Editor/Terrain/PerformanceStudy/`。不添加正式菜单，不创建Scene／Prefab。空闲Editor显式编译后，经既有CLI eval调用`TerrainRenderBench.Run(inputPath, newOutputDirectory)`；输出目录每批另建，不能覆盖旧证据。需先按项目要求检查内存／磁盘并核对未处于Play。

`assess.py`读取当前r4的身份、样本与PNG，并生成展示副本。正式落地仍需针对既有真实坡形和局部地形事务单独接入；本轮未改变它们，CL阶段继续。
